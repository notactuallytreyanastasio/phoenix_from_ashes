From Ashes to 1.0

This is the story of Phoenix Framework—how Chris McCord's vision of a productive Elixir web framework evolved from a single commit into a production-ready platform that would change how developers think about real-time web applications.

19 months. 17 releases. 284 decisions captured. From the initial commit on January 18, 2014 to the landmark 1.0 release on August 28, 2015, Phoenix grew from a Rails-inspired experiment into the framework that proved Elixir could be both productive and performant. Every architectural decision, every community contribution, every pivotal moment—captured in a decision graph you can explore.

The First Decision

Router Architecture: Compile-time vs Runtime

#37 #38 architecture

The very first architectural decision would define Phoenix's DNA:

decision #37
Initial Router Architecture: Compile-time vs Runtime matching
Use Elixir macros to generate pattern-matched route functions at compile time. defmatch/defroute_aliases macros create efficient dispatch.
CHOSEN
Compile-time Macro Generation
defmatch macro generates pattern-matched functions. Routes become function clauses. Zero runtime route lookup cost.
Elixir's pattern matching handles dispatch
ALTERNATIVE
Runtime Route Matching
Store routes in ETS, match at runtime like typical frameworks.
More flexible but slower

This decision—leveraging Elixir's metaprogramming for compile-time route generation—gave Phoenix its speed advantage from day one.

Interestingly, the GenServer-per-request approach was initially chosen (#42), then reconsidered (#43). Commit 8a3bddfb8 refactored to use try/catch instead—performance and simplicity won over process isolation for simple request handling. The lesson: sometimes the "Erlang way" isn't always the right way.

February 6

The Scope Macro

83344fc #54 #92
decision #54
Route organization: Scope macro for namespacing
Namespace routes under paths like scope '/admin' do. Organizes large apps. Admin panels, API versioning patterns emerge.
scope "/api", Api do
  resources "/users", UserController
end

scope "/admin", Admin do
  resources "/posts", PostController
end

This small addition had outsized impact. It made Phoenix's router feel immediately familiar to Rails developers while enabling clean API versioning and admin namespaces.

The Endpoint architecture was a major refactor that established Phoenix's plug pipeline pattern:

decision #69
Plug pipeline architecture
How to compose middleware for request processing?
option #70
Plug composition (chosen)
Functional middleware pipeline - call/2 convention
pipeline :browser do
  plug :accepts, ["html"]
  plug :fetch_session
  plug :protect_from_forgery
end

pipeline :api do
  plug :accepts, ["json"]
end

Each plug was a simple module with init/1 and call/2. No magic—just function composition. The request/response cycle became transparent and testable.

PubSub Design

Distributed Broadcasting

#78-80 pubsub
decision #78
PubSub backend architecture
How to distribute messages across nodes?
DEFAULT
pg2 (Erlang process groups) (#79)
Built-in Erlang distributed messaging. Zero dependencies.
OPTION
Redis adapter (#80)
For deployments across separate clusters

The adapter pattern meant Phoenix Channels could scale horizontally. Broadcast a message on one node, every connected client on every node receives it. This was the foundation for million-connection deployments.
